# 临期自动用卡设计

状态：已按下列约定在独立新聊天实现本地 v0.3.7，完成相关离线/模拟检查及本地包校验。真实兑换、无 Codex 窗口后台、退出/唤醒和安装升级仍待实机验收；未用真实卡测试。

任务边界：原聊天独立处理胶囊与官方更新按钮重叠及其诊断；移除旧“系统通知”入口、调整通知规则和新增“临期用卡”由新聊天实施，保留原 v0.3.6 修正。此前生成的效果图仍是旧版示意，尚未按右侧打勾、四字名称、移除常驻副文案和保留“检查更新”等约定重画；实施以本稿的最新文字约定为准。

## 已确定的目标

作为胶囊可提供给其他用户的本地功能。每人在自己的 Windows 电脑上运行胶囊并使用自己的 Codex 登录，不提供集中托管账号、云端代管或远程执行服务。电脑关机、休眠或胶囊退出时不能执行；电脑正常运行且胶囊驻留时，不要求打开 Codex 桌面窗口。

只处理即将到期的免费重置卡，不自动购买重置、不新增“额度用完就用卡”规则，不改变模型、代理、主题或其他功能。官方更新按钮与胶囊重叠属于另一项故障，本设计不混入其修复。

## 方案选择

1. 整体集成 Magpie：会引入 Go 程序及其账号、网关、路由等体系，远超本功能需求，不采用。
2. 借鉴 Magpie 的临期检查、最早到期优先、兑换前再次检查和互斥思路；在现有 Rust/Tauri 项目中实现最小本地模块，通过已有 Codex app-server 会话调用公开接口。推荐采用。
3. 部署服务器代管：可解决用户电脑关机的问题，但需要另外处理托管授权、服务与账号管理；用户已选择本地功能，此次不采用。

Magpie 为 MIT License，若实际移植其代码，必须保留对应版权和许可说明。只借鉴规则、独立编写实现时，记录参考来源即可，不把整个项目作为依赖。不得因为现有 Magpie 功能可用，就推定其内部网页接口适合本项目；本项目继续不直接读取 auth.json 或调用网页内部 wham 接口。

## 用户能理解的开启与关闭

- 新安装、旧版本升级和未知账号均默认关闭。升级不能视为同意自动用卡。
- 设置入口采用四字名称“临期用卡”，与“开机启动 / 检查更新”保持一致；沿用现有右侧打勾样式，有勾为开启，无勾为关闭，不使用独立滑动开关。首次确认且保存成功后才能打勾。
- 不在菜单行下方常驻“提前 30 分钟尝试使用”说明，关闭、开启时均不显示该副文案。把自动含义和提前时间放在悬停提示、首次授权说明里，避免被误认为点击立即用一张卡。保留现有底部“检查更新”的位置和功能。
- 初版固定提前 30 分钟，不新增任意分钟输入框。30 分钟是初版建议值；它是开始检查并尝试的时间，不是精确执行或兑换成功保证。
- 去掉独立的“系统通知”菜单项、悬停说明，以及旧的卡片临期 Windows 弹窗；临期提醒继续保留胶囊红点及其已有展示规则。卡片详情里的到期时间继续保留，不能把删除通知按钮理解成删除卡片信息。此调整与自动用卡一并实施，不混入重叠修复。
- 第一次开启前，只读取得可辨识的当前 ChatGPT 账号。用户确认该账号的持续授权后，才保存开启状态；保存失败不得开始执行。授权包括该账号今后新获得的临期卡，直到关闭，不转移到其他账号。
- 确认说明必须写清：在这台电脑上自动兑换该账号符合条件的临期卡；无需逐次确认；已有额度不与重置后的额度叠加，重置时间可能改变，兑换成功不能撤销；电脑和胶囊必须在运行。
- 未确认开启时不兑换，不因用户没有点“取消”或没有回应而默认授权。开启以后，临期时不再弹出等待确认的对话框，否则不能称为自动用卡。
- 关闭后阻止新兑换；已经发送出去的请求不承诺撤销，继续核实并记录它的最终结果。关闭状态保存失败时，本会话立即停止新兑换，同时明确提示未能保存，不能显示为已持久关闭。
- 开机启动与自动用卡是两个独立开关，不擅自启用开机启动。用户退出胶囊时，程序及检查一并退出，不另装服务或任务计划，不唤醒睡眠电脑。
- 无法辨识账号、登录类型不适用或切换到未授权账号时，显示暂停/未开启，不能沿用前一个账号的许可。账号标识或计划发生不能确认兼容的变化时，重新授权，宁可暂停也不跨账号执行。

## 后台执行

- 复用现有 quota.rs 的 app-server 请求、账号复核及错误分类，不为自动用卡再启动一套并行额度轮询。
- 自动功能关闭时，保留现有跟随 Codex 的额度服务启停行为。
- 自动功能已获授权时，即使没有 Codex 桌面窗口，也允许额度 worker 运行。胶囊和详情等窗口仍遵循原显示与释放规则；后台用卡不要求创建 WebView，也不自动打开 Codex。
- 沿用约 60 秒正常额度刷新及现有失败退避。启动、从休眠恢复后依据当前时间和新数据判断，不重放缓存里的过期任务；不为倒计时每秒请求接口。
- 将卡片 expiresAt 与额度窗口 resetsAt 明确区分。只有卡片到期时间进入未来 30 分钟范围才是临期触发条件，自然额度恢复时间不是卡片到期时间。
- 自动兑换前必须有本轮新读到的账号、卡片及额度状态；持久化缓存只能帮助展示与恢复执行记录，不能直接据此兑换。

## 单次兑换流程

1. 检查账号许可及当前登录身份，刷新额度和可用卡片明细。不能取得一致、适用的账号身份时停止本轮。
2. 从已返回、可核实 ID 与有效到期时间的可用卡中，优先选择最早临期者。仅有数量时继续正常显示数量，但不猜测目标卡或到期时间。明细截断不使有效额度失效，也不要求数量等于明细长度；只能处理明细里已核实的具体卡，不能声称知道不可见卡的最早到期时间。
3. 满额、没有适用额度窗口或官方不允许兑换时不强制用卡。也不自动修改官方允许用卡设置。现有窗口解析不支持的计划/窗口不能猜测其用卡资格。
4. 在同账号互斥范围内再次检查许可、当前身份、目标卡和最新额度，防止用户刚刚手动兑换、自然恢复或关闭设置后仍发起旧任务。
5. 在发送前持久化账号、目标卡 ID、请求的幂等键和待核实状态。持久化失败时不发送兑换请求。使用显式 creditId，禁止省略后由服务端任意挑选另一张卡。
6. 调用 account/rateLimitResetCredit/consume。reset 或 alreadyRedeemed 表示该逻辑请求兑换已完成；先持久化结果，再补读额度。额度仍旧时显示“已用卡，额度同步中”，不能因为未回到 100% 就再次用卡。
7. nothingToReset 表示本次没有适用窗口；保留卡、停止本次写请求，之后只在新的额度读取显示条件发生变化时重新评估。新的明确尝试可以有新的幂等键，但必须仍核实同一卡和许可，不能把拒绝当作允许连续消费其他卡。
8. noCredit 或目标卡消失时只补读状态，并结束该卡的自动尝试；本次临期阶段不自动换成其他卡重发，后续 60 秒轮询也不能绕过。直到原目标卡的到期时间过去，才允许在新读取的状态上评估其他尚未到期卡。仅凭明细中消失不能断言是本程序、别的程序或用户用掉，也可能是卡片过期或明细截断。初版的这项保守策略可能错过短暂异常后恢复的目标卡，但避免把失败转化为自动消费另一张卡。

## 防重复与无法确认的结果

- 同一账号同一时刻只允许一个兑换。覆盖同一 Windows 用户下多个胶囊实例的并发，并在互斥后重新读取执行记录。程序重启不能使已处理卡或待核实请求变成全新任务。
- 请求超时、连接中断或答复格式错误时，不能直接认定未兑换。先补读，并仅对原账号、原 creditId、原幂等键做有界复核；不换新键或下一张卡“再试一下”。
- 初版建议：同一未知请求至多做两次恢复尝试，最早分别在约 60 秒和 300 秒后；仍不明确则暂停该账号的自动兑换，保留状态并提示用户核查，不无限请求。若卡已过期，不再发起新的兑换，只保留未决结果。
- 进程在发送后、保存成功前崩溃时，下次先恢复待核实请求，不能按新任务兑换。执行记录损坏、缺失关键字段或不可写时，该账号的自动兑换停止，普通额度显示继续工作。
- 本机互斥不等于跨电脑、跨工具互斥。开启说明提醒同一账号不要同时在多个设备或工具启用自动用卡；显式卡 ID、执行前补读和服务端幂等只是减少冲突，不能宣称已经协调 Magpie 等其他程序。
- 多张卡临期时一次仅处理一张。确定目标并准备首次发送时，一并持久化“下一张卡最早允许评估的时间”为该目标卡的 expiresAt；在此之前只能核实或按规则重试原目标，不能另选一张。成功后也保留该限制，避免额度响应仍旧导致下一轮误耗第二张卡。切换开关、重启和另一个本机实例不能清除此限制。
- 原目标的到期时间过去后，先刷新状态，再评估其他卡。额度已经恢复满额时不继续用卡。初版不提供“连续使用所有临期卡”模式；两张同时到期的卡不承诺都能有效使用，重置不能叠加成 200% 额度。

## 用户可见结果和本地记录

设置入口应能看出：未开启、等待临期、缺少卡明细、账号不匹配/需登录、暂不可兑换、兑换结果待核实、已用卡待同步，以及最近一次结果和时间。界面不得把“已配置”显示成“保证到期前成功”。

Windows 通知只用于自动用卡的结果：成功或失败且需要用户处理时，每个事件最多通知一次。成功但额度尚未同步时说明“已用卡，额度正在同步”。不在每次使用前再通知或等待确认，不对每次轮询或重复 nothingToReset 刷屏；首次开启的明确授权仍必需。移除旧通知开关后，不再由遗留的 notifications_enabled 值阻止这些结果通知。Windows 通知被禁用或勿扰模式可能使弹窗不可见，不得声称通知一定送达；无论弹窗是否显示，结果仍可在软件内和本地诊断中查看。

诊断继续使用白名单和轮转，只记录必要的时间、分类、数值与不透明关联编号。完整卡 ID 和请求幂等键为内部持久化执行记录所需，不写入公共日志或公开发布说明；不记录凭据、账户明文、完整 RPC 或提示词，不上传账号和执行记录。

## 必须验收的情形

| 情形 | 预期 |
| --- | --- |
| 用户没有开启、拒绝首次授权或没有回应 | 不兑换 |
| 已授权，卡临期，胶囊运行但 Codex 窗口未打开 | 在条件允许时自动尝试，不再等确认 |
| 关机、休眠、胶囊已退出 | 不执行，不声称仍有代管 |
| 唤醒时仍未过期 | 先读新状态，符合条件才尝试 |
| 唤醒时卡已过期 | 不补兑、不拿另一张卡替代旧任务 |
| 同一账号重启，或重复额度通知 | 不重复产生兑换任务 |
| 账号切换、身份不明、登录失效、CLI 不支持接口 | 停止兑换并显示原因，不影响正常界面 |
| 卡只有数量，或某张缺少 ID/到期时间 | 不猜测；仍可正常显示权威数量 |
| 明细截断但某张临期卡完整可核实 | 只评估该具体卡，不否定整个额度快照 |
| 全满、自然刚恢复、服务端不允许用卡 | 不强制兑换，不承诺“不论用量必用” |
| 用户/其他工具已用卡、同时出现多张临期卡 | 再检查，不盲目换卡或连续清空 |
| noCredit、目标消失或兑换成功后的下一轮轮询 | 原目标到期前不另选一张；刷新不能绕过临期阶段限制 |
| 网络断开、服务端已处理但响应丢失 | 保留原幂等请求，先核实，不把超时当未用 |
| 返回成功但额度尚未同步 | 标记已用卡待同步，禁止重复消费 |
| 发送前记录失败、执行记录损坏 | 不发送，提示自动兑换暂停 |
| 关闭设置发生在准备发送或请求已经在途 | 关闭阻止新请求；在途请求核实最终结果 |
| Windows 通知被禁用、勿扰或系统没有显示通知 | 执行许可不变，软件内仍能查看结果 |

优先复用现有 Rust、设置、quota、diagnostics 与原生菜单检查。新增模拟 RPC 验证目标卡、幂等键、并发、异常结果与持久化边界；真实桌面还要验证无 Codex 窗口时的后台运行、退出和唤醒。模拟通过不能代替真实兑换成功；未经单独授权，不用用户的真实卡进行测试。

## 实施前的技术边界

- 以官方公开的 consume 接口和本机 CLI 登录态为基础；旧 CLI/服务端拒绝时显示不可用，不添加网页内部接口兜底，也不为了探测能力而兑换一张卡。
- 公开文档对 Usage 页面和助手自动用卡有资格限制；这些限制不能直接推定为第三方 consume 接口的同一阈值。应用自己的授权不代表绕过服务端资格。真实可用范围及更新后的接口行为需要实际环境证据。
- 初版采用提前 30 分钟、本地执行、单账号明确授权、无云代管和不逐次确认的方案。未知结果的恢复间隔等工程参数按上述保守策略实施，并结合现有接口能力验证；不能把参数设定当成真实兑换成功的保证。
- 本设计只新增临期自动用卡，不把已有“识别额度已恢复”的逻辑改成消费卡；观察到重置与主动兑换是不同的操作。

## 设计复核

已做一次独立只读复核。复核指出 noCredit/目标消失后的“禁止换卡”可能只约束当前请求而被下一轮轮询绕过，现已明确为持久化的临期阶段限制，并同时覆盖兑换成功但额度尚未同步的情况。没有修改产品代码、调用兑换接口或消耗真实卡。
